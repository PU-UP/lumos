- `lumos_agents.py` 统一四角色身份、字段权限、持久步骤和只读诊断。默认 Lumos 先提出意图/候选，需要时串行调用资料管理员、AIPM 或仓库维护者；专业角色各处理一次，资料管理员可追加一次关键词检索。跨角色结果整批校验、原子保存。纯对话只调用 Lumos。
- 自动整理直接交资料管理员，全量任务复核与到期主线复核直接交 AIPM。默认 Lumos 草案中的业务变更必须经专业角色返回，不能直接落库。直接专业角色请求可委派其他专业角色，维护者禁止派发业务写入。每轮最多协调、三种专业处理、一次资料检索和一次综合；不循环调用。
- intake ID 即 episode ID，步骤/尝试保存角色、模型选择、规则/代码摘要、输入版本、开始结束、候选摘要与目标、失败类型；不保存内部推理或原始工具输出。最终回执和业务变更同批提交，返回失败可以读回恢复；重试保留旧尝试，过期接续标记中断并拒绝旧领取者写入。
- 网页增加角色选择、资料页和协作记录页。巡检记录失败、过期、失效结果；支持从确切 episode 直接向维护者反馈。手动巡检不依赖模型，**定时巡检未启用**。当前诊断覆盖已保存执行记录，未扫描代码质量、磁盘或外部服务日志。
- `lumos_knowledge.py` 统一当前笔记、来源、正式文档及登记材料的关键词检索；默认排除归档笔记，确切引用带笔记 revision 或文档/材料 hash。每次最多100条命中，可缩小关键词范围；不是语义检索。资料管理员只读目录与有界片段，不声称通读全库。
- project-materials 需选择脉络后显式登记，最大20MB，拒绝越界路径、符号链接和目录联接。不可变副本存入数据根 `sources/materials/`，与数据库一起备份；旧版本纳入完整性检查。文本、HTML、DOCX/PPTX正文可提取；PDF、图片、XLSX等首期只登记原件与解析状态，不做OCR。未登记的项目文件仍不在数据备份范围。
- 桌面通过同一 CLI、角色规则和业务校验接续；外部协调计划标注未记录内部步骤，不虚构历史执行角色。没有实现桌面原生线程同步或跨宿主进程隔离。

## 1. 当前基础与改造范围

| 当前能力 | 位置 | 重构时的处理 |
| --- | --- | --- |
| 固定输入、领取、租约、版本依据、回执 | `lumos_intake.py` | 沿用；补充角色、episode 与步骤身份 |
| Codex 计划生成、不同场景的提示词、后台循环 | `lumos_worker.py` | 分开角色规则与执行方式，保留有界执行 |
| 原子保存、历史、文档候选与恢复 | `lumos.py`、`lumos_tasks.py` | 继续作为唯一正式保存入口 |
| 全量任务复核、主线复核、跟进日期 | `lumos_task_review.py`、`lumos_intake.py`、`lumos_followup.py` | 归入 AIPM 的职责范围；确定性日期校验继续由程序执行 |
| 自动整理与 Lumos 归档的授权区分 | `lumos_notes.py`、`docs/notes.md` | 保留；跨角色处理不能扩大授权 |
| 页面问题、连续对话和保存回执 | `web/work-model.js`、`web/chat.js`、`web/overview.js` | 共用角色身份、问题身份和处理进度 |

角色、模型、工作空间和执行实例是四个不同概念。同一模型可以承担不同角色；`lingguang`、`lumos` 仍是资料范围；一次执行只是某个角色处理一个具体请求。新增角色不会建立另一套任务库或知识库。

第一阶段先按职责顺序执行，复用现有队列。当前 `context_basis` 校验整个空间的记录与问题，直接增加并发会让无关改动也使计划失效。后续具备确切读取范围和对象版本检查后，才对互不依赖的步骤开放有限并行；不能通过取消版本检查换取并发。

## 2. 四个角色的责任

| 角色 | 负责的结果 | 可主动做的事 | 应交给谁 |
| --- | --- | --- | --- |
| Lumos | 理解意图、综合答复、协调不同工作的目标与取舍 | 读取相关上下文、直接回答、分派必要步骤、汇总结果和关键问题 | 排期与任务接续交 AIPM；资料加工与检索交资料管理员；运行问题交仓库维护者 |
| AIPM | 主线阶段与任务安排合理、关键缺口有人承接 | 检查依赖和阶段节点，按授权调整内部计划、负责人、关心日与下一步，接续原问题 | 缺少资料交资料管理员；跨项目资源或目标取舍由 Lumos 综合，必要时问王牧楠 |
| 资料管理员 | 来源可追溯、当前结论可辨、资料能准确取回 | 整理笔记、登记资料与版本、提取事实、维护来源关系、检索、报告矛盾和过时引用 | 事实对任务的影响交 AIPM；需要业务判断的矛盾交 Lumos |
| 仓库维护者 | 故障可定位、重复问题可归并、改进建议有证据 | 按计划或手动触发只读巡检，检查运行记录、失败与版本冲突，形成诊断发现 | 是否修改由王牧楠触发维护工作；业务判断仍交 Lumos/AIPM |

Lumos 的协调责任不要求所有输入都调用四次模型。纯问答可以由 Lumos 直接完成；已有确切资料可直接引用；只有涉及资料加工、任务判断或诊断时才增加对应步骤。后台到期复核可直接交 AIPM，再将结果汇入 Lumos 的统一工作视图。

界面维护首期是仓库维护者按需开展的专项工作，不增加常驻角色。修改代码的维护会话与自动只读巡检使用不同权限，不能因为同叫“仓库维护者”而继承写代码权限。

## 3. 权限与字段归属

### 3.1 各角色提交什么

以下“提交”均指调用经过校验的业务工具；模型不直接修改数据库、不可变来源或工作文件。

| 内容或动作 | 主责角色 | 保存条件 |
| --- | --- | --- |
| 对话答复、分派与综合建议 | Lumos | 建议保留建议身份；只有实际保存成功才声称已更新 |
| 任务、主线进展、内部排期、问题接续 | AIPM | 固定原文或确切来源、当前版本、对应空间授权及完整影响范围 |
| 明确承诺 `due`、完成/取消、实际完成日期 | AIPM 承接明确事实 | 保留王牧楠的新明确安排或结果依据；不能由推理、日期或其他 Agent 的建议生成承诺 |
| 人员职责理解 `assessment` | AIPM | 有历史任务/来源支持并保留不确定性；正式任命和组织字段仍走现行授权流程 |
| 笔记正文与整理版本 | 资料管理员 | 仅当前正文对应的整理授权；新编辑、恢复、删除使旧执行失效 |
| 来源登记、知识依据、版本引用及综合文档候选 | 资料管理员 | 原件与出处保留；正式文档仍遵守 begin/commit 和编辑暂停要求 |
| 笔记 Lumos 归档 | 协作流程的最终保存步骤 | 用户已触发，当前版本整理成功，全文承接完整，知识与任务结果同批保存 |
| 运行诊断、重复问题、处理建议 | 仓库维护者 | 写入诊断记录，不写业务进展、不修改代码或自动改变运行配置 |
| 正式决定、主线创建/归档、外部消息、删除等 | 对应现行授权入口 | 本方案不放宽现有确认或授权条件 |

`planned_due` 是当前内部计划，`due` 保留明确约定，`completed_on` 保存实际完成日期；角色拆分不改变这些含义。跨主线安排须核对阶段目标、前置依赖、负责人协作和下游影响。关键事实未知时复用确切问题，不靠机械改期消除提示。

### 3.2 如何防止职责串用

每一步由服务端绑定角色、工作空间、任务类型、可读对象和允许调用的工具；保存时同时核对用户授权、来源及对象版本。前端或模型提交的角色名称只表达意图，不能提升权限。引用另一角色的结果必须带原始来源和版本，不能把 Agent 摘要当作新的用户证据。

知识冲突由资料管理员列出相互矛盾的证据；排期冲突由 AIPM 说明受影响阶段；Lumos 综合仍无法判断时提出一个具体问题。发生冲突时保留当前正式内容和候选，不采用最后返回的 Agent 自动覆盖前者。

桌面对话若持有任意文件写入或 shell 权限，角色规范只能约束遵循工具的协作，不能提供操作系统级隔离。自动角色应使用受限的业务工具；若需要更强隔离，再落实独立进程权限和文件访问限制，不能只增加一个角色字段便宣称隔离完成。

## 4. 协作流程

### 4.1 工作对话或进展输入

1. 固定原话、入口、工作空间、确切关联对象及本次授权，建立 episode。
2. Lumos 判断是纯讨论、资料请求还是工作更新；纯讨论保留对话，不强行制造任务或依据。
3. 需要资料时由资料管理员返回来源片段、版本、日期与不确定性；原始输入始终可追溯。
4. 需要接续任务时，AIPM 根据原话、来源和当前主线提出变更，承接每个选中且仍开放的问题；未答部分保持原身份。
5. 保存入口校验范围、来源、授权、版本及业务规则，一次提交本次相关结果。
6. Lumos 根据实际回执给出结果；“正在处理”“等待信息”“已保存”和“业务完成”明确区分。

### 4.2 笔记整理与归档

“自动整理”只分派给资料管理员：保存当前整理正文和固定原稿，不更新任务、不归档。公开资料核查沿用当前笔记规则，补充与原话分开。

“Lumos 归档”建立跨角色处理：资料管理员逐项列出原文要点及承接去向，AIPM 接续任务和主线，最后将知识、任务、问题与笔记归档同批保存。待外部结果的问题可以转入主线继续跟踪；未识别、未承接的原文不能被“已归档”掩盖。

中间结果只是候选。任何必需步骤失败，均保留笔记未归档和可重试的步骤；笔记在处理中被编辑、恢复或删除，依赖旧版本的步骤停止应用。正式文档候选需要独立编辑会话时，显式等待可安全保存条件，不提前宣布整篇处理完成。

### 4.3 AIPM 主动管理

触发来自新明确反馈、已有主线复核日、任务关心安排变化或手动“更新全部任务”。确定性的日期检查由程序完成，不为每次页面刷新调用模型。

同一空间、同一轮安排去重；前台输入优先，低频巡检让位。复核先看主线阶段，再看相关任务，已能安排的直接处理，必要问题按主线汇总。收到“暂无变化”也保存答复和后续核对安排，不当天重复催问，不推定完成。

自动发生的只有复核与内部安排；到货、实测、同事接受任务等外部事件仍须有真实输入。服务未运行期间不宣称执行过巡检；恢复时按确切安排补一次检查，合并重复到期事件。

### 4.4 资料入库、检索与纠错

首期范围是已登记资料和 `project-materials`。先建立目录清单并按需提取，之后处理新增或变更文件；不把每轮对话变成全目录重读。文件名和修改时间只能帮助定位，不能当作内容结论或事件日期。

每项资料保留稳定 ID、版本/哈希、原始位置、可知的作者与事件日期、获取日期、用途和确切引用。文本提取保留页码、段落或表格定位；图片、扫描件和无法可靠提取的材料显示解析范围与缺口。压缩包作为资料处理，不执行其中脚本。

检索先走确切任务/来源引用，再做关键词搜索；返回片段、适用版本、冲突及是否已被替代。检索索引可重建，不成为第二份权威知识。只有实际检索案例证明需要时，再增加语义检索。

项目资料现位于数据根之外，不在现有完整备份范围内。建议纳管时保留原件，并将被正式引用的必要版本纳入可备份的数据范围；大文件另建可恢复清单。明确备份覆盖之前不称“已可靠入库”。

资料纠正先保留新证据和替代关系，再列出受影响的当前知识与任务；AIPM 重新核对依赖和安排。没有新结果时不自动改任务状态；旧来源和旧判断继续可追溯。正式文档与引用关系按现有事务流程处理，不绕过文件编辑保护。

### 4.5 仓库巡检与修复交接

程序即时记录失败、超时、过期执行、保存冲突等事件；维护者按手动触发或低频汇总分析，建议每周在服务运行时执行一次。这个频率是待讨论的默认值，本稿不创建自动任务。

巡检输入包括代码版本、角色规则版本、运行摘要、受影响对象及必要的脱敏错误。先用确定性检查发现问题，再让模型解释有价值的异常；日常巡检不调用真实业务故障测试，不擅自运行修复脚本。

发现记录包含严重程度、现象、影响、证据 episode、可能原因及不确定性、建议、首次/最近发生时间和次数。相同问题合并为一条并保留各次证据。状态区分待处理、已知悉、已安排、待验证和已验证；已知悉不代表修好，测试通过也不冒充真实使用验收。

王牧楠明确触发修复后另建维护 episode，关联原发现并限定修改范围。界面维护也采用此流程。一个角色不能通过在日志里写“需要修复”给自己授予修改权限。

## 5. Episode 与操作日志

### 5.1 三个层次

| 对象 | 表示什么 | 稳定身份 |
| --- | --- | --- |
| episode | 一次用户请求、一次明确到期复核或一次巡检的完整处理 | 首次接收时生成；重试沿用；新的用户补充建立新 episode 并关联前次 |
| step | 某个角色负责的一个可独立恢复步骤 | 在 episode 内稳定，记录前置步骤和输出去向 |
| attempt | 同一步骤的一次实际执行 | 每次执行不同，保留 claim、起止、结果和失败原因 |

角色自己的“操作日志”是这些事件按角色筛选的视图。跨角色交接共用 episode，避免四份独立日志无法对齐。模型会话 ID 只是执行端的关联信息，不取代 episode；更换模型或执行器不改变业务身份。

### 5.2 建议记录字段

| 分类 | 必要内容 |
| --- | --- |
| 请求与授权 | episode ID、触发类型、原始 request ID、入口/对话引用、工作空间、输入及版本引用、授权依据 |
| 执行范围 | step/attempt ID、角色、前置步骤、读取对象版本、允许的工具与写入范围 |
| 可复现环境 | 代码版本、角色规则/提示词版本、执行器和实际模型；运行参数按实际可获得项记录 |
| 事件 | 时间、事件类型、来源角色、目标角色、受影响对象、简明原因与结果引用 |
| 保存证据 | 稳定操作 ID、提案摘要/哈希、校验结果、正式批次和回执、改前/改后版本引用 |
| 运维 | 开始/结束、耗时、错误分类、是否可重试、取消原因、实际可获得的用量；缺失数据明确未知 |
| 反馈 | 王牧楠的原话、发现 ID、关联结果/步骤、处理决定与验证证据 |

事件可包括接收、分派、领取、来源读取、提案形成、校验拒绝、保存成功、等待信息、失败、重试、取消及反馈。原因写成可审查的业务依据和来源，不采集或要求模型的内部思维链。

### 5.3 状态与恢复

episode 对外显示排队中、处理中、待信息、失败、已处理或已停止；必要时另标“部分结果已保存”。步骤分别显示自己的状态，不把一个步骤完成显示为整次工作完成。单条未答业务问题可以长期保留，而本次已完成的整理 episode 正常结束。

| 情况 | 处理方式 |
| --- | --- |
| 同一请求重复提交或响应丢失 | 沿用 request/operation ID，查询已保存回执，不创建第二份任务 |
| 模型执行失败但尚未保存 | 保留输入与已完成的候选步骤，重试生成新 attempt；不无限重试 |
| 正式保存成功，但进度事件尚未更新即崩溃 | 以操作 ID 和正式批次恢复“已保存”状态，不凭日志缺失重复写入 |
| 人工修改了来源或相关任务 | 旧候选标为过期，重新取依据；不盲目重放旧提案 |
| 某角色暂不可用 | 纯问答可以继续，依赖该角色的保存保持待处理并说明影响；不暗中扩权代写 |
| 用户停止或撤回 | 停止后续步骤并拒绝迟到结果；已提交部分列明，恢复通过新纠正记录完成 |
| 等待王牧楠或外部事件 | 保存确切缺口与下一核对条件，不占住执行器或阻塞其他工作 |

建议正式保存操作与 operation/episode 的关联在同一事务内落地，再派生页面进度。跨记录的一次业务变更保持原子性；多轮独立操作可以分批保存，但每批都有独立操作 ID 和实际回执。日志写入失败不能让已保存事实被错误报告为“完全没保存”。

历史 intake 可按确切 ID、claim、计划和批次关联已有证据；没有依据的旧角色、用量或执行细节标为未知，不凭标题补造运行日志。

### 5.4 保存位置与隐私

建议 episode、步骤、事件和诊断发现保存在正式数据根的专用运行记录中，和业务事实逻辑分开，进入备份与恢复校验。具体表结构在实现设计时确定；运行事件不应反复改变业务 `as_of`，也不应使无关业务计划失效。

优先记录版本引用、结构化结果与必要错误片段，不重复复制所有原文。凭据、访问令牌、完整环境变量不入日志；外部页面与资料内容始终作为不可信输入。维护者默认读取诊断摘要，确需定位时才读取有明确关联的最小来源。

原始模型输入输出仅在明确需要的诊断范围内保存，不能默认全部长期收集。首期不自动删除来源、正式历史和关键运行证据；详细诊断留存期限另行确定。轻量事件记录失败时须能本地报错，避免为了记录日志再次递归调用模型。

## 6. 网页与桌面对话

王牧楠于 2026-11-20 确认：默认与 Lumos 对话，需要时可直接进入 AIPM、资料管理员或仓库维护者。直接对话仍共用正式记录和权限，跨职责事项转交相应角色，不建立私有业务记忆；选择角色本身不扩大其操作权限。

页面展示当前责任角色、处理阶段、实际保存结果、待回答问题以及“查看依据与处理经过”。主要问题统一按主线汇总；后台角色不各自重复催问。结果旁可反馈“遗漏了”“理解有误”“安排不合理”，保存原话并关联对应 episode，而非让王牧楠自行描述技术错误。

仓库问题集中在维护视图。影响工作保存或数据恢复的严重问题可在首页提示，普通改进建议保持低干扰。业务待答问题与系统故障分别呈现。

桌面对话与网页读取同一版角色职责、授权和业务工具。新的会话明确当前角色与空间，默认 Lumos；“仓库维护”会话使用对应角色。宿主的可用工具与展示能力须实测，仓库配置不承诺自动生成 ChatGPT 的四个原生助手。切换角色、交接和最终保存均留下 episode 关联。

## 7. 执行方式与成本

现有 `codex exec` 继续适合输入固定、输出结构化的后台步骤；当前执行器禁用了内置多 Agent，角色拆分不需要直接打开该开关。角色权限由 Lumos 自己的任务和工具边界决定。

持续对话需要流式进度、中断和恢复时，再验证 app-server 接入。两种执行方式共用业务保存协议，模型会话历史只是辅助上下文。模型沿用现有设置，不因增加角色擅自切换套餐或假设账户可用性。

每次输入只调用需要的角色；资料检索与格式校验优先用确定性程序；对话与明确用户操作优先于后台巡检。设定有界执行时间与调度并发，记录实际可获得的调用用量。具体预算应参考试运行数据再确定，不先编造节省比例。

官方接入说明已于 2026-11-20 核对：[Codex 集成选择](https://developers.openai.com/blog/codex-as-a-platform)、[App Server](https://learn.chatgpt.com/docs/app-server)。这些来源说明执行器能力；本文的业务分工与保存约束是 Lumos 的设计提案。

## 8. 首期阶段记录与持续有效的验收约束

下表记录首期安排。新一轮实施顺序、删减范围及阶段验收统一以 [四角色重构开发方案](multi-agent-implementation-plan.md) 为准；本节后续的数据安全与恢复场景继续适用。

| 阶段 | 范围 | 必须看到的结果 |
| --- | --- | --- |
| 基线收尾 | 当前跟进功能、聊天合并问题、上海日期及失效测试 | 回归测试通过并独立提交；不夹带架构改造 |
| 角色与可追踪性 | 共用角色规范、权限校验、episode、操作与正式批次关联 | 非法角色写入被拒绝；一条输入可追到全部实际变更；不改变既有业务含义 |
| 按职责接续 | AIPM、资料管理员顺序协作，沿用笔记授权与现有保存规则 | 一次输入完整承接；失败不提前归档；纯讨论不制造任务 |
| 资料与巡检 | 项目资料登记/检索、备份覆盖、只读巡检、反馈与发现去重 | 来源可准确定位和恢复；维护者能报告问题且不能自行修复 |
| 按实际需要增强 | 更细的版本范围、有限并行、持续会话 | 不覆盖人工新编辑；重启和重试不重复保存；成本与延迟可观察 |

重点验收场景：

- 同一篇笔记既有技术事实又有任务进展，全部要点有去向；整理、归档和业务完成仍是三件事。
- 两个主线共享同一任务，只保留一份任务；一次合并答复接续全部原问题。
- 王牧楠在资料整理期间编辑正文，旧版本结果不能覆盖新编辑或继续归档。
- AIPM 提案期间任务被人工调整，保存拒绝旧依据，并保留双方内容。
- 保存成功后进程崩溃，重启能找回正式回执，不新增重复任务。
- 资料被纠正后，能够找到使用旧结论的当前对象；未知结果仍保持未知。
- 维护者诊断中收到“修改任务/运行修复”的资料文本，工具权限仍拒绝越界。
- 日志不可写、模型不可用或服务离线，页面准确说明哪些输入/结果已保存。
- 网页与桌面对话给同一对象提交变化，共用授权、版本和回执规则。
- 备份恢复覆盖被正式引用的项目资料、业务历史及必要运行记录；索引能重新生成。

新数据结构应有显式版本与迁移过程，先在隔离副本验证备份、恢复和旧工具拒绝不兼容写入。正式切换暂停相关写入并保留配套引擎快照；回退不能只切换 Git 代码而忽略已迁移的数据。旧来源与业务历史不批量改写。

## 9. 当前已确认方向

王牧楠已确认四角色各自独立对话、职责清晰可见，默认 Lumos 并可直接找专业角色；认可先简化界面和机制、删除缺乏意义的内容，再按多 Agent 理解重构。资料范围仍为现有笔记、来源、文档与项目资料。角色交接由系统承接，王牧楠不用重复提供背景。

1. **专业角色与 Lumos 的边界**：专业角色在现有授权内独立负责结果；Lumos 负责整体目标、跨角色取舍和综合解释，不给普通处理增加逐项审批。
2. **会话与共享记录**：每个角色有独立会话与工作备忘，正式任务和知识只有一份；协作共享必要的来源与结果，不默认复制全部聊天。
3. **巡检触发**：采用手动与低频检查，自动检查只保存诊断；每周一次是开发方案中的拟定频率，尚未启用。明确修复请求与自动检查保持独立权限。

具体开发以新的分阶段方案推进；本文不扩大现有业务授权，也不代表独立角色会话、交接恢复和低频巡检已经实现。
