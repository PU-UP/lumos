# Lumos 四角色重构开发方案

日期：2026-11-20。王牧楠已认可“四个独立助手、职责可见、共享正式记录、按需协作”的机制方向。本文件给出实施顺序与验收条件；本轮只交付开发方案，不开始产品代码重构。

## 目标与当前差距

Lumos 是默认工作替身，AIPM、资料管理员和仓库维护者各有独立对话、明确责任与可接续的工作记录。使用者可以直接找任何角色，跨职责工作由系统交接，不要求重复解释背景。

当前基线为 `e695f7f`：已有角色权限、串行协作步骤、固定来源、关键词检索和只读检查；128 项 Python 与 148 项前端测试在该提交交付时通过。对话仍按工作空间组织、角色按轮次选择，缺少会话固定归属、角色工作收件箱与完整的交接恢复机制。三项主导航只是过渡版本，不能作为多 Agent 机制的验收结果。

开发优先级是：先减少概念和重复机制，再做实独立角色与协作，最后增加确有用途的主动工作。沿用标准库、现有本地服务和正式数据根，不建立通用 Agent 平台。

## 一份职责约定

| 角色 | 持续负责的结果 | 直接操作范围 | 需要交接的情况 |
| --- | --- | --- | --- |
| Lumos | 理解目标、综合工作概览、协调取舍、向王牧楠交付结果 | 对话、必要分派、综合解释 | 任务安排给 AIPM，资料加工给资料管理员，故障给维护者 |
| AIPM | 主线、阶段、任务、依赖、内部排期与关键问题 | 现有授权内的业务更新和跟进；人员职责理解 | 资料缺口给资料管理员；目标或资源取舍交 Lumos 汇总 |
| 资料管理员 | 笔记与资料完整、结论有出处、信息可准确取回 | 授权的正文整理、来源登记、检索、知识候选 | 结论影响任务时交 AIPM；重要事实矛盾交 Lumos |
| 仓库维护者 | 运行问题可定位、诊断有证据、改进有去向 | 自动检查只保存诊断与建议 | 明确修复请求进入有范围的维护流程；巡检不能给自己授权修改代码 |

专业角色在权限内自行办完并答复，Lumos 不逐项审批普通处理。直接找专业角色时，由该角色负责向王牧楠交付；只有影响整体工作的结果或待取舍问题汇入 Lumos。共享结果引用原始证据，不把 Agent 判断转成用户事实。

现有笔记授权、明确承诺、实际完成日期、正式组织任命、外发与删除规则继续生效。角色选择和交接都不能扩大权限。

## 删除与保留

| 现有内容 | 本次处理 | 必须保留的能力 |
| --- | --- | --- |
| 全局“灵光／Lumos 仓库维护”选择器 | 移除；后台按确切项目与来源保留范围 | 工作资料与仓库维护记录不能混写 |
| “工作／对话／记录”统一功能导航 | 替换为四个角色入口，不并存两套主导航 | Lumos 默认打开工作概览，专业角色可直接进入 |
| 同一对话逐轮切角色 | 删除；会话绑定角色，跨角色建立交接 | 角色明确、原话与历史不丢失 |
| 独立的资料与运行门户 | 合入资料管理员、仓库维护者的工作区 | 检索、登记、诊断与完整追溯 |
| 四角色各自复制任务、知识、问题状态 | 不建立；均引用同一正式记录 | 来源、版本、授权与修改历史 |
| 多处重复的职责文字、提示词约束、状态转换 | 收拢到统一角色约定和既有处理入口 | 服务端仍独立校验权限，不能只靠提示词 |
| 大量原始来源、重复失败提示、技术参数默认展开 | 改为结果与下一步优先，细节按需打开 | 原文、旧版本、失败尝试及恢复证据 |
| 旧页面链接 | 跳转或打开对应角色中的原对象 | 收藏、任务引用和历史回执可继续使用 |

项目范围由确切对象和当前会话背景确定，创建会话时固定并可见。出现歧义时询问“这件事属于哪个项目”，不能靠角色名称或关键词静默跨空间写入。进入维护者也不意味着获得全部业务资料的读取权限。

## 阶段一 四个独立角色空间

**交付：能分别与四个助手持续工作，旧入口同步收拢。** 角色身份与页面一起交付，不单独上线只有角色名称的空壳。

1. 固定四个角色入口。桌面显式展示，窄屏可用角色选择器；每个入口显示一句职责。Lumos 首页保留待答问题与项目进展，并有自己的对话。
2. 对话有持久元数据：稳定 ID、所属角色、资料范围、标题与状态。服务端绑定角色，后续轮次不能用前端参数切换身份；更换模型不改变角色。
3. 每个角色有独立会话列表、草稿与最近工作结果。复用一个对话组件和现有业务视图，不复制四套网页实现。AIPM 放任务与人员，资料管理员放笔记与资料，维护者放运行问题。
4. 工作备忘保存当前目标、未完成事项和来源引用，随版本更新；它是恢复上下文的摘要，正式事实仍以共享记录为准，不另建四份知识库。
5. 清除全局空间切换、逐轮角色切换和重复主导航。旧链接映射到新位置；当前业务对象的 ID 与空间归属不变。

会话元数据纳入现有正式存储、校验、备份与恢复。需要扩展记录类型或存储约束时，提供显式版本迁移与旧引擎写入保护；迁移从这一阶段开始在隔离数据验证，不拖到最后。

**阶段验收：** 四个角色各开两段对话，切换、刷新和服务重启后，角色、历史、草稿与未完成事项不串用；伪造角色提交被拒绝；原工作概览、笔记操作和任务详情仍可用。此时不要求新增自动巡检或复杂协作。

## 阶段二 可追溯的职责交接

**交付：一件事可以由多个角色处理，责任、结果与失败接续都能看清。**

1. 复用 `intake` 作为 episode，扩展现有步骤记录表示交接：发起角色、接收角色、目标、确切来源、允许动作、前置步骤、处理状态和结果引用。
2. 各角色的待办与操作记录从同一 episode 派生。交接明确标为“Lumos 转交”等系统工作，不写成王牧楠说过的新消息，也不把所有后台事件塞进人工聊天。
3. 每次交接只给必要背景；回传结果、依据与剩余缺口。知识修改由资料管理员负责，任务修改由 AIPM 负责；普通问答不强制调用其他角色。
4. 一次必需的跨角色业务更新仍由既有入口整批校验、原子保存。角色步骤完成不等于业务保存，更不等于实际任务完成。
5. 继续串行、有界执行。交接状态持久化；失败保留责任方和可恢复位置，重试先核对来源版本与已保存回执。仅复用仍有效的候选结果，不能盲目重放。
6. 同一问题保留统一身份，入口角色负责答复，Lumos 概览只汇总需要王牧楠判断的事项。相同问题不由多个角色重复催问。

**阶段验收：** “整理评审并调整后续安排”能完成 Lumos → 资料管理员 → AIPM → Lumos 的接续；直接找 AIPM 可独立办完。中途失败、服务重启、响应丢失、重复提交和人工修改来源时，均不丢输入、不重复保存、不覆盖新内容。可从任一结果追到交接与实际变更。

## 阶段三 专业工作与主动接续

**交付：每个角色持续负责一类工作，日常动作与提醒有明确去向。** 本阶段分角色交付，优先 AIPM 与资料管理员，再接维护者。

| 角色 | 本阶段工作 | 验收结果 |
| --- | --- | --- |
| AIPM | 统一接管既有全量任务复核、到期跟进与主线问题；先检查阶段和依赖，再形成内部安排；将结果送到自己的工作区并汇入 Lumos 概览 | 只问关键缺口；无新事实不标完成、不改变真实进展日期；同一问题不重复出现 |
| 资料管理员 | 统一笔记、来源、正式文档和已登记项目资料；整理、入库与检索有明确入口；纠正后列出确切受影响引用，交 AIPM 核对 | 自动整理只动笔记；Lumos 归档完整承接原文；能取回正确版本，未解析内容明确说明 |
| 仓库维护者 | 形成可跟踪的问题清单，按错误类型和确切对象归并重复发现；保留发生次数、影响、证据与处理状态；手动检查优先，随后加入低频检查 | 问题可定位和反馈；已知悉不等于修复；自动巡检不能改代码、配置或业务记录 |

主动工作由明确事件触发：新的工作反馈、既定跟进节点、获授权的整理/归档请求、相关资料变更或巡检到期。资料变化先核对差异与引用，不自动导入整目录或改写所有结论；界面刷新不触发模型调用。

低频巡检拟按每周一次实现，使用现有后台服务和持久化执行标记。离线期间如实显示未执行，恢复后合并补查一次；用户输入优先于巡检。普通改进留在维护者空间，影响保存或恢复的问题才汇入 Lumos 首页。

首轮检查限定已保存执行记录、来源与引用有效性及现有执行器状态。代码质量扫描、磁盘巡检和外部服务监控不顺带加入。修复请求仍由现有代码维护环境执行并关联原问题；不新增可自动修改仓库的常驻进程。

**阶段验收：** 用同一组模拟工作贯穿任务进展、笔记整理、资料纠正和运行故障，四个角色的结果与待办各有去向，王牧楠不需要在页面间搬运信息。来源中的指令不能触发越权修改。

## 阶段四 历史迁移与整体收尾

**交付：旧工作可接续，重复实现可删除，正式服务可恢复。** 迁移方案与用例在阶段一建立，本阶段完成整体验证和正式切换。

1. 历史对话有明确且一致角色时据实关联；多角色混合或归属不明的对话保留原样并标注。继续讨论时建立对应角色的新会话，链接原历史，不按标题猜测身份或改写原话。
2. 保留笔记、任务、来源、问题身份及已有承诺。旧草稿与未确认发送请求先恢复原归属和请求身份，再转入新入口；不能因升级丢稿或重复发送。
3. 验证备份覆盖新会话、交接、诊断和固定资料版本。迁移先在隔离副本完整演练，正式切换暂停相关写入，保留匹配的代码与数据快照。
4. 回退使用匹配版本；正式切换后的新增工作必须先保留并核对去向，不能直接恢复旧快照丢掉新记录。迁移失败时保留原正式位置，不能出现两个可写主库。
5. 按调用关系删除已无用途的旧页面实现、重复角色配置与重复处理分支；旧 URL 仅留必要映射。保留安全校验、原文和恢复历史。
6. 网页与桌面入口采用同一角色约定、保存协议和 episode 关联。桌面依宿主实际能力显式绑定角色与会话；不承诺自动创建或同步 ChatGPT/Codex 的原生对话。

**阶段验收：** 正式切换前通过历史兼容、完整回归、桌面/手机流程和隔离恢复测试；切换后核对关键对象与回执。真实使用重点观察是否还要重复解释背景、是否分得清谁负责、纠正能否被后续接续。测试通过与长期使用验收分别记录。

## 开发工作包与提交顺序

| 顺序 | 主要涉及位置 | 提交边界 |
| --- | --- | --- |
| 1 | `lumos.py`、`lumos_intake.py`、`lumos_agents.py`、存储与迁移测试 | 会话固定归属、范围和兼容校验先完成 |
| 2 | `lumos_web.py`、`web/navigation.*`、`web/chat.*`、现有业务视图 | 四角色入口与独立历史；同时移除替代掉的交互 |
| 3 | `lumos_worker.py`、`lumos_agents.py`、`lumos_intake.py`、回执视图 | 持久交接、结果归属、重试恢复与问题去重 |
| 4 | `lumos_task_review.py`、`lumos_followup.py`、`lumos_notes.py`、`lumos_knowledge.py` | 各角色复用现有业务能力，合并重复规则 |
| 5 | 维护诊断、既有 Worker、备份恢复与验收文档 | 低频接续、整体迁移、清理和交接 |

每个提交保持测试通过；中间状态不切入正式服务。阶段一作为第一个可整体体验的交付，阶段二作为机制闭环交付；阶段三按专业角色拆分，阶段四完成正式验收。需要人工决定的目标或权限变化集中提出，普通实现选择依已认可方向推进。

不预设具体交付日期。先以阶段一的迁移复杂度和实际工作量校准后续安排，阶段完成以验收结果为准。

## 验证与范围控制

- 每阶段运行 `py -3 -m unittest discover -s tests -v` 与 `node --test tests/*.test.cjs`；使用等价 Python 3.12+ 路径时记录环境。
- 前端阶段检查桌面与窄屏、键盘操作、切换角色、历史、草稿和旧链接；后端阶段检查越权、版本冲突、幂等、停止与恢复。
- 模型端到端验证使用隔离的模拟资料，核对真实保存结果，不把测试数据写进正式历史。正式数据只用于获授权操作与切换后的读回核对。
- 本轮开发不包括新增界面维护 Agent、并行调度、无限 Agent 群聊、第二套数据库、语义索引、OCR、外部通知或桌面原生对话同步。先把四角色职责与接续机制做实。
- 整体成功标准：四个助手各有独立对话和持续责任；一件事能自然跨角色完成；重要结果和问题只保留一个正式身份；使用者理解与操作负担低于当前版本。
