# Lumos 最小设计提案

日期：2026-09-23，Asia/Shanghai。状态：已按第一轮 reviewer 意见修订，待复审，未进入实现。

## 1. 推荐与成功标准

推荐以**现有 Agent 对话为入口、可修改的本地工作区为工作场所、Markdown 与 SQLite 共同持久化、Notion 为可选阅读投影**。

先做一个单用户、单主要工作位置、按需运行的小工具与 Agent 操作约定，不做聊天应用、常驻后台、云共享数据库或多 Agent 编排平台。用户只交流问题和材料，Agent 负责寻找已有工作、推进讨论、维护理解和关联成果。

核心验收不是“信息记下来了”，而是：在不提供旧聊天记录的情况下，另一位 Agent 能从工程和数据中正确继续一项实际工作，知道目前判断、关键依据、未决问题、相关成果、下一步及其条件；用户无需重新讲背景。一个月后，恢复同样可行，但不能把旧状态假装成仍然有效。

基本路线已获本轮反馈支持；具体保存与恢复约束按评审意见修订，仍需复审后再进入实现。当前只交付设计文档。

## 2. 主要使用流程

用户可以直接说“先聊没有 RTK 时的建图定位”“这个结果和昨天不一样”“继续上次的问题”“我忘了我们为什么这样选”。

Agent 内部完成以下循环，可在一次对话中反复发生：

1. 找到相关工作及最近理解，按需要读取依据、行动和成果。
2. 直接讨论、研究、分析或产出；过程中保留尚未收敛的方案和疑问。
3. 在一个有意义的讨论段落结束、获得重要材料、作出决定或准备切换问题时，保存最小必要变化。
4. 检查变化影响的判断、行动和成果，读回确认保存成功。
5. 回答当前问题。通常不报告整理流水账；影响方向的理解变化用一句话提醒。

“继续”默认直接推进；“忘了”先给几句话概括，再按追问展开。若两个候选问题都合理，只问一个能消除实质歧义的问题，例如“你指定位路线还是数据回流？”。找不到记录时明确说缺的是哪次决定、哪份材料或哪项结果，并说明仍能做什么，不补造记忆。

Agent 应自行读取已授权且可访问的文件和来源；只有信息在他人手中、权限不足或含义确实不清时才请用户补充。材料存在于工作区时，不要求用户重新转述。维护行动不等于获得联系他人、安排提醒、发布内容或执行外部操作的权限。

第一版的“主动”指对话期间主动整理、发现矛盾和提示应复核内容；关闭 Agent 后不会自行研究、提醒或执行任务。下次进入时重新检查相关等待条件和时间约束。

## 3. 最小组织结构：工作脉络、记录、文件

### 3.1 一个可持续理解的问题就是一条工作脉络

工作脉络是稳定的身份和一个当前理解入口，可以是专题、阶段工作或项目，不强迫三层树形结构。创建条件是问题值得跨对话继续、已积累依据，或有后续成果与判断；一次性解释无需独立建档。

初始只需要“入职准备”这条脉络。八个方向放在同一份准备地图中，作为覆盖面；不自动生成八个任务、八套文件夹或八份长文。

当“首款产品的建图定位流程与约束”产生独立方案、证据和后续问题时，再形成一条相互关联的脉络，同时连接硬件、产品流程和软件接口。可先在同一文档展开，内容确实需要独立维护时再拆分。

脉络默认持续维护；也可等待条件、暂存或归档。“阶段成果交付”不自动结束脉络。项目只是确有阶段目标时采用的称呼，不新增一套对象或任务状态镜像。

每条脉络只有一份当前理解入口，按内容需要包含：

- 正在解决的问题、目标和边界；
- 当前判断、关键理由、适用条件和反证；
- 仍有价值的备选方案、分歧和未决问题；
- 下一处值得推进的问题，或等待什么条件；
- 相关决定、行动、材料和成果的入口。

这不是固定填表：无内容不建空章节。长研究、比较、实验设计和交付物放在工作区独立文件，入口只保留足够继续工作的综合理解。稳定技术经验从进度记录中提炼到相关方案或研究正文；只在确有复用价值时单独成文，不先建百科体系。

### 3.2 少量结构化记录解决精确性问题

建议 SQLite 保存脉络身份和文件指针，以及以下记录。实现可使用共享记录表与按类型验证，不要求每一类建独立数据库或服务。

| 记录 | 必须能表达的内容 | 不代表什么 |
| --- | --- | --- |
| 陈述／依据条目 | 内容、谁说或观察到、来源、适用范围、发生时间与记录时间、核实情况 | 用户转述不等于硬件规格已证实；来源声称不等于实测 |
| 决定 | 谁决定、选择、理由、条件、依据、取代哪项决定、何时生效 | Agent 推荐与用户沉默不是决定 |
| 行动 | 具体动作、负责人（可未知）、最小完成条件、状态及完成依据、依赖／等待条件、可空的跟进日期 | 研究方向、长期愿望或开放问题不是任务；普通行动完成不等于技术验收通过 |

Agent 建议、假设和探索优先留在工作文档并明确身份；当它们影响重要判断、需要被其他文档引用或等待验证时，才提取为带类型的记录。无需逐句结构化。

行动建议使用“待做、进行中、受阻、完成、取消”这些足够区分的状态。仅讨论候选动作时不创建已承诺行动；用户明确计划或已授权范围内的必要执行步骤可以自动登记，执行边界另行遵守原授权。负责人不默认归用户，日期不猜。

普通行动由 Agent 根据明确意图提炼最小完成条件并直接登记，不因用户没预先写验收标准而进入确认队列。例如“明天找同事聊一下同步问题”，条件就是完成这次交流，跟进日期按发言当天的时区解析；用户后来明确说“聊完了”，可记为“完成，依据：用户报告”，保留来源。交流结果尚未提供时留空，不追问标准，也不把同步技术问题标为已解决。

重要实验、技术指标和产品交付继续按对应验收条件判断。条件不清时可先登记已明确的行动，把技术验收缺口保留在相关工作中；只在它实质影响执行或结果判断时澄清，不能自行降低要求。“试验已跑完”与“指标通过”分开，用户报告通过也不冒称 Agent 独立验证。一份分析完成不等于路线确定，一次讨论结束不等于整个方向完成。取消保存原因，不伪装成完成。

### 3.3 文件承载真实工作

文件角色包括当前理解、工作草稿／方案、研究分析、原始材料、成果。角色只是元数据，按实际工作创建目录，不给每个角色预建一套空树。

方案可以不断修改、比较可以保留未胜出的候选、实验分析可以有中间结果。Lumos 不只是最终结论集；保留这些内容的判断标准是“是否帮助继续工作或解释重要选择”，而不是“是否已经完成”。

生成的正式成果需关联脉络、依据和生成时的内容版本。需要可编辑源文件的成果同时保留源文件；只有 PDF 而没有源稿时要明确可编辑性缺口。临时预览和可完全再生的中间文件无需永久保留。

## 4. 文档、数据库与来源的唯一职责

| 信息 | 正式维护位置 | 其他位置如何使用 |
| --- | --- | --- |
| 问题解释、当前综合判断、方案与探索 | Markdown 工作文档的已登记版本 | 数据库只登记身份、版本、关联和必要定位信息，不再维护另一份判断正文 |
| 行动状态、跟进日期、决定及其取代关系 | SQLite 记录 | 文档引用记录 ID；需要列表时生成只读视图，不手填第二份状态表 |
| 来源元数据、核实边界、证据支持的具体主张 | SQLite 依据记录与文件登记 | 文档作简短引用，原始内容仍在来源文件中 |
| 原始资料、图片、数据、成果正文 | 必要文件及其版本 | SQLite 保留路径、校验值、用途和关联，不把二进制塞进记录字段 |
| 谁在何时因何改变了正式理解 | SQLite 变更记录＋保留的旧文档版本 | 日常入口展示当前理解，需要追溯时读取历史 |
| 阅读简报、Notion 页面、检索索引 | 从上述内容派生 | 有版本和新鲜度信息，不接受独立工作状态维护 |

当前文档可以解释决定的含义，但正式选择与理由由决定记录负责；解释通过 ID 指向它，并记录基于哪个版本。纠正决定时检查引用它的当前文档。文档不能独立改写决定，也不能复制行动日期再各自维护。人类可读的输出允许重复展示，重复的权威编辑入口不允许存在。

每条可引用对象有稳定 ID；重命名和搬目录不改变身份。关联只记录实际有用的“属于／相关、依据、支持或反驳、产出、依赖、取代”等关系，不先建设知识图谱。SQLite 中的关系连接到记录、脉络或文件版本，避免只靠标题和脆弱的 Markdown 标题锚点。

来源保存原始地址或文件位置、作者／提供者、可知的发布日期／发生时间、实际获取时间、定位片段及保存情况。时间未知就留未知，不能用文件修改时间充当事件日期。材料哈希用于检查相同内容，不把不同独立来源仅因文字相似而合并。

关键用户陈述保留必要原句或忠实摘录，附“本次用户输入”等可用定位；可获得会话链接时附链接，但不以平台聊天记录为唯一依据。用户转述张总的话，应标成“用户转述／待核实”，不是已经查证的首款硬件清单。

重要可变来源应保存足够上下文的快照或原文件；大数据可以保留完整数据集，或选定足够验证结论的片段与精确清单。若为节约空间不保存完整数据，要明确丢失哪些复现能力。必要材料不能只留旧电脑绝对路径；要么纳入数据包，要么确认独立备份及可恢复位置。凭据不写入文档或来源记录。

## 5. Agent 恢复上下文与修订理解

### 5.1 进入新对话或更换 Agent

未来的工程入口约定保持简短：说明产品角色、读写入口、证据纪律和数据根定位。新 Agent 先检查数据与工程版本兼容性，再按当前问题恢复：

1. 读取工作索引：有哪些活跃脉络、各自入口、最近实质更新，以及最近推进的焦点。
2. 通过用户表达、别名、最近焦点和关联检索匹配问题；最近焦点只是线索，不能压过明确的用户意图。
3. 读取命中的当前理解、相关未结行动、有效决定及最近实质变化。
4. 沿引用读取会影响本次回答的来源和成果，检查其适用范围、过时条件及相互矛盾之处。
5. 内部组织“当前问题—判断与依据—不确定性—下一步”，直接回答。

索引首先使用数据库字段查询和文本搜索；SQLite 全文索引可按需求加入并可重建，不引入向量数据库。上下文过长时先读摘要，再逐级展开；不能仅凭摘要完成需要具体实验证据的判断。

离开一个月不是所有知识失效，但相对日期、硬件条件、人员和阶段安排需要复核。把“最后有证据支持的状态”和“今天确认的状态”区分开。若无法读取数据或不兼容，只能作临时讨论，明确无法恢复或持久保存的具体部分。

### 5.2 更新判断与纠正

| 新输入 | 默认处理 |
| --- | --- |
| 普通补充、资料、解释更清晰 | 找现有脉络，更新文档／来源及关联，自行完成 |
| 新实验或有来源的事实 | 保存条件和结果，判断支持／反驳什么；不默认升级成普适结论 |
| Agent 提案或“也许可以” | 作为建议／假设保留，不成为用户决定或已承诺行动 |
| 用户明确选定阶段路线 | 建决定并更新相关理解，创建确有承诺的行动，不终结长期问题 |
| 用户纠正旧陈述或旧选择 | 保存新输入依据，以修正／取代关系替代旧记录，检查受影响文件和行动 |
| 证据冲突但无法判断真伪 | 并列保留范围和冲突，暂缓依赖争议前提的结论，提出最小验证 |

“用户最新说法”可决定用户意图，但不能自动覆盖相反实测事实。修正是“原记录理解错了”，取代是“当时正确、现在改选了”，二者保留不同理由。

影响方向的变化用一句话告知，例如“你修正的是验证阶段，不是生产选型；我会把原先记录的‘已定路线’改回阶段假设”。普通拼写、归档、去重不用逐项汇报。

历史保留关键输入、选择及理由、反证、实质范围变化和被替代的内容版本；不保存模型内部推理、完整逐轮聊天或每次工具输出。这里只需要能解释当前状态和恢复文件版本的变更记录，不建设可重放所有业务状态的事件溯源系统。

纠正首先作用于这次工作。重复出现且确有共同原因的操作问题才进入少量改进候选；不把每个个案升级为永久规则，不在第一版复制完整反馈管理系统。

## 6. 本地运行与数据一致性

### 6.1 推荐技术取舍

SQLite 适合一个主要工作位置：记录关联、事务、检索和整体迁移都比较直接，无需数据库服务。Markdown 可被现有 Agent 阅读、编辑和比较。纯文件方案开始更轻，但行动状态、引用和版本关系散落后容易产生重复维护；服务器数据库目前增加运维和联网依赖，没有对应的并发收益。

第一版建议提供一个小型本地命令行入口供 Agent 调用，集中承担恢复查询、保存一批变化、验证和备份恢复。普通用户不用记命令。Python 标准库即可作为首选实现基础；具体命令和表结构在评审后确定。本轮不写代码、不安装依赖、不创建数据库。

不要求所有 Agent 使用同一模型或聊天产品，只要求它能读取工程入口、调用本地工具、操作工作文件并遵循来源和更新约定。不支持这些能力的 Agent 只能阅读导出的简报，不能承诺等价连续工作。

建议数据根与工程分离，示意为 `lumos-data/`，由本机配置指定；也允许部署在工程目录下的明确忽略路径。必要结构只有数据库、工作文件、保留版本、原始材料／成果和可重建缓存；不按八个方向预建目录。数据库存相对数据根的路径，原电脑路径只作历史来源说明。

### 6.2 从编辑到提交的防覆盖与文件版本

SQLite 事务不能同时原子提交任意文件。推荐保留**先保存不可变文件版本，再在一个数据库事务里切换记录和文件版本指针**，但防覆盖必须从编辑开始，不能等原文件被重写后才检查。

第一版采用单编辑会话：同一数据根只有一个 Agent 编辑会话，从读取编辑基线持续到保存与读回结束；其他 Agent 可讨论和读取，不能并行改写。人工编辑应在该会话前完成保存，或等它结束后继续，期间暂停对工作文件的写入（包括编辑器自动保存）。这是运行约束，不是逐条内容审批。工具锁只约束遵循入口的 Agent，不能把拿到锁当成人工已经停写；不能满足暂停条件时只保留独立候选，不替换工作文件或提交这批变化。

最小保存流程：

1. **保留读取基线**：读取相关数据库版本和工作文件实际内容，保留基线副本、文件身份／相对路径及哈希。新文件以“路径不存在”为基线。工作副本已有未提交修改时也须读入，不能只从数据库旧版生成内容。
2. **生成独立候选**：Agent 把修改写到本批次的候选文件，不原地重写工作文件。基线和候选在保存完成或冲突解决前均保留；有价值的未提交候选同样纳入备份。
3. **替换前复核**：确认单编辑约束仍成立，重新检查整个批次相关文件的内容／存在性及数据库版本。遇到改动、删除、重命名或新路径已被占用，停止该批次，不覆盖、不先提交一部分记录。保留基线、当前内容和候选，基于三者重新合并；无冲突部分由 Agent 处理，实质含义冲突才请用户判断。合并后重新建立基线并再次检查。
4. **保存正式版本**：检查通过后先将候选写成不可变文件版本，校验内容；再用一个 SQLite 事务提交记录、关联、当前版本指针及变更说明，并检查数据库基线未过期。已登记版本是正式恢复依据，工作副本只是可编辑入口。
5. **刷新工作副本并读回**：实际替换前再次核对工作文件与读取基线一致，保留原内容后才更新。若事务提交后发现文件变化，则保留双方，标记“正式版本已提交、工作副本冲突”，停止刷新并重新合并，不回写覆盖人工内容。读回数据库、正式版本与工作副本的一致性；有冲突不能报告全部保存完成。

哈希检查与文件替换之间仍有时间窗口；第一版依靠明确的单编辑约束排除这段时间的其他写入，不宣称能保护任意不遵守约束的编辑器。发现持续写入就停止替换、保留候选，恢复单编辑条件后再合并。不能以“原子替换文件”或“提交前哈希相同”冒充通用并发编辑保护。

用户可以在 Agent 编辑会话之外自由编辑工作副本。Agent 在恢复、编辑和备份入口发现已有改动及新增文件，按上述流程吸收；草稿可以保存为“探索中”，无需先成为结论。可见副本与已登记版本不一致时，明确视为草稿或冲突，不能静默丢弃。

中断处理：不可变版本已写但事务未提交时，正式版本仍是旧版，保留候选及新版本供恢复；事务已提交但工作副本未刷新或只刷新一部分时，以数据库登记的一整批正式版本为准。副本已等于该批次候选则无需重写，仍等于基线才可刷新，两者都不等则保留为冲突。事务结果不明时按批次 ID 查询，避免重复创建行动／决定。第一版保留孤立版本，不自动清理。

上述流程只做成服务本次工作的小型保存工具，不扩展出分支、通用合并引擎、实时协作、文件监控服务或通用版本管理系统。版本和关系只覆盖实际引用的内容。

必要文件缺失或损坏时报告具体受影响记录，阻止依赖它的确定性结论；不能靠缓存或 Notion 页面悄悄补成完整证据。

## 7. 正式数据、缓存、Git 与备份迁移

### 7.1 数据边界

| 类别 | 内容 | 保留与迁移 |
| --- | --- | --- |
| 工程版本 | 代码、操作约定、模板、工程设计、依赖锁定与迁移工具 | Git；未提交工程修改也须在备份中保存补丁或完整工程快照 |
| 正式持久数据 | SQLite、被引用的文档版本、决定／行动／来源／关联／变更历史、必要原始材料、成果与编辑源稿、发布映射 | 独立于 Git 备份，完整迁移 |
| 未提交工作 | 可编辑草稿、新增实验分析、未登记材料与人工修改、有价值的候选及未解决冲突的基线／双方内容 | 同样备份，恢复后标为待吸收或冲突，不能假定可重建 |
| 可重建缓存 | 搜索索引、当前摘要视图、临时渲染、已保存原文的文本抽取、阅读投影 | 可以不备份；删除后不能丢失唯一资料或用户编辑 |
| 本机与安全配置 | 数据根、临时锁、凭据、设备专属路径 | 配置模板入 Git；实际凭据另行安全恢复，锁不迁移 |

只有“输入、方法及所需依赖仍可获得、且没有独有人工编辑”的产物才可归为缓存。无法保证重建的有用分析和正式输出按持久数据保存。

### 7.2 一致备份

建议在有数据变化的使用日结束时做一次本地快照；版本升级、数据迁移和重大重整之前强制做。初始可由 Agent 在本次使用结束时调用工具，不声称存在尚未配置的每日定时任务。暂定保留最近 7 个使用日和 4 个周末／周度快照，是否删除更早版本以后再按空间需要决定。

快照要求从扫描开始到最终校验完成，全程暂停 Agent、人工编辑、编辑器自动保存、材料导入和其他产出程序的写入。先结束编辑会话并保存编辑器缓冲区；未写到磁盘的内容无法由备份保护。仅锁数据库不够。无法满足暂停条件时不承诺完整快照，不引入实时快照机制来绕过这一约束。

完整快照步骤：

1. 选择普通备份或迁移快照，冻结写入并等待在途批次结束，记录最后批次 ID。未吸收草稿保留其身份，不强制升级为正式结论。
2. 对整个持久数据与未提交工作中的文件范围生成备份前清单 M0：相对路径、文件大小和内容哈希，包含新文件、候选和冲突副本，而非只扫描数据库已引用文件。数据库及 WAL 等配套文件按步骤 3、6 单独备份验证，不参加源端与目的端的这组字节比对。排除缓存、凭据、临时锁及备份输出本身，明确固定排除范围；备份输出放在被扫描范围之外。对应工程快照也在冻结范围内。
3. 通过 SQLite 备份接口得到一致数据库副本，不直接复制正在使用的数据库主文件，也不依赖恰好没有 WAL。数据库单独做逻辑一致性检查，不把活动数据库主文件的字节哈希当作事务一致性的证明。
4. 按 M0 复制全部必要版本、原始材料、成果、未提交工作和恢复配置说明，生成目的端清单。外置必要数据必须同样冻结并纳入核对，或交付已校验的不可变独立数据包。
5. 所有复制结束后，对源端相同完整范围重新扫描并计算 M1，核对 M0 与 M1 的路径集合和全部内容哈希，再核对目的端与 M0 一致。任何新增、删除、重命名或修改，以及未结束的写入，都使本次尝试不完整；恢复静止条件后从整组扫描重新备份，不能只补复制变动文件就宣称完成。这覆盖“先复制旧 A、后复制新 B”的失败场景。
6. 清单记录备份时间、数据库 schema 版本、工程提交／发行版本、未提交工程差异、文件格式版本和最后批次 ID；保存对应工程快照，不能只依赖远端仍保存那个提交。检查数据库完整性、外键、引用文件与哈希，以及冻结期间无新提交。
7. 全部通过后才标记快照完成；不完整尝试不能覆盖上一个可用快照。**普通备份**结束可恢复原位置写入；**迁移快照**完成后旧位置继续冻结，按 7.3 切换，失败重试期间也不自动解冻。

前后清单核对是暂停写入约束的补充，不是允许并发编辑的证明；若已知备份期间发生过写入，即使最终内容改回原样，也应废弃该次尝试并重试。

同磁盘快照便于撤销，不能覆盖设备损坏。第一版验收要求至少一份完整数据备份进入用户选择的独立磁盘或受控存储；如需要异地加密，使用现有成熟备份工具，不自己设计加密。恢复密钥另存于数据包之外的可靠位置。

### 7.3 工程与数据配套恢复、迁移切换

普通恢复演练只使用隔离副本，不把副本当第二个正式工作位置。迁移到新电脑、服务器或云主机则按以下顺序接管，不能沿用普通备份“完成后解冻”的收尾：

1. **冻结旧位置**：停止所有写入并禁止人工编辑，记录迁移冻结状态，重启工具后仍拒绝写入，不能靠临时进程锁维持。按 7.2 生成一致迁移快照，完成后旧位置继续只读。
2. **在新位置恢复**：校验完整标记和清单，恢复对应工程与数据，配置新数据根并单独恢复凭据。检查 schema／文件格式兼容性；不支持该数据版本的程序拒绝写入。检查数据库、引用和哈希，识别未吸收草稿，重建缓存，保留 ID、时间和关系。
3. **隔离试运行**：旧位置保持只读。新位置只用于限定的恢复验证，由新 Agent 核对决定、行动、成果和缺口，再按 6.2 保存一次试运行变化；不用于同时开展另一条正式工作，也不触发 Notion 发布或其他外部副作用。记录相对迁移快照的试运行批次，便于判断保留或放弃。
4. **新位置接管**：验证通过后明确登记新位置为唯一可写工作位置，保留试运行中已验证的有效变化；旧位置继续只读，不能再各自延续工作。此后若要切回旧设备，应从当前权威数据重新做迁移，而不是直接解冻旧副本。
5. **失败或取消**：先停止新位置试运行并放弃其作为工作状态的资格，再恢复旧位置写入。含有价值内容的试运行差异导出为非权威归档，告知哪些变化未进入旧位置；需要保留的内容以后作为普通补充，在旧位置重新核对并保存，不自动合并数据库或覆盖旧数据。不含独有内容的试运行副本可弃用；两边不能分别继续。

若需升级数据，先在快照副本上运行明确版本迁移并验证；失败保留原数据。回滚使用升级前的整套工程与数据，不把旧程序直接接到已升级数据库。第一批没有旧 schema 可迁移时只验证不兼容拒写与整套恢复，不先建设通用 schema 迁移框架。

迁移完成后无需旧电脑路径、旧会话缓存或 Notion 才能理解旧工作。网络来源和发布凭据暂不可用时，本地保存的上下文仍可继续；未备份的外部资料无法恢复要如实说明。

Git clone 单独不足以恢复 Lumos；数据库单独也不足以恢复。此限制应出现在未来的运行入口与恢复说明中。

## 8. 其他设备阅读与 Notion

先验收本地核心流程，再在获授权后接入一个 Lumos Project 和一篇展示子页，作为首个展示增量。该子页提供适合手机阅读的简报：当前结论、两三条关键理由、必要限制、下一步及成果入口，标注实质更新日期、证据时间边界和生成时间。本地 Markdown 保留可维护来源，Notion 不成为本地运转、恢复或迁移的依赖。

HTML 阅读包移至后续按需导出，不列入第一批实现或必做验收，不同时建设附件打包、传输和手机打开验证的第二条展示链路，也不先建设托管服务。

Notion 启用后默认一个名为 **Lumos** 的 Project 作为统一入口。专题、事件或成果按需要用子页面承载；项目入口做导航和少量当前重点，不重复维护每个任务的日期或状态。

本地内容是权威源。Notion 页面只展示筛选后的阅读投影，不同步完整内部过程。采用“每个稳定主题一个规范页面、重要阶段成果按需留快照”的方式，不每轮新建页。

建议在授权启用后，遇到重要结论变更、形成阶段成果或用户要求时，由本次 Agent 运行发起更新；常规补材料不立即刷新所有页面。无常驻服务时不承诺实时更新。

一次发布保存本地来源版本集合、目标 Project／页面 ID、内容哈希、尝试时间和实际核验结果。重试沿用页面 ID；查询已有页面后再创建。写后回读正文、成果链接、入口及返回导航。部分成功就记录部分成功；重要内容已改但 Notion 发布失败时简短提示“本地已更新，阅读页仍是旧版”，不声称同步完成。

本地新版本产生时，派生的阅读内容可标记过时；旧 Notion 页面不能在离线状态凭空改变，因此页面始终显示其实际内容更新时间与证据边界。重新发布前只替换 Agent 管理的内容区域；若有人直接编辑该区域，保留差异并核对，不把远端编辑自动写回决定／行动，也不无声覆盖。

手机上的本地绝对路径不可用：展示成果时必须附可访问文件、支持的附件或已授权托管链接；没有可用渠道就写清“文件仅在主工作位置”，不能交付假入口。Notion 不是原始材料备份，页面删除不导致本地数据丢失。

当前不创建或修改 Notion。展示增量只验证一个入口、一篇子页及一次更新，不先做批量发布平台；尚未授权或暂不可用时，本地核心验收可以独立完成，展示验收标为未开展。

## 9. 用入职准备走通七种情况

以下 A 为本次已知输入，B—G 为设计推演，不是已发生的研究、决定、试验或工具验证。示例 ID 只是帮助评审追踪。

### A. 首次输入八项准备

创建一条“入职准备”脉络 C1 和一份准备地图，完整保留八个方向的含义：算法架构与仓库规则（感知、定位、地图、规划、控制、业务大脑）；LiDAR SLAM 与建图定位；感知训练／部署／标注／回流／脱敏；规划控制与覆盖／沿边；传感器、同步、标定与布局；现有软件及 IoT／HMI；完整产品流程；AI coding 与 workflow 效果验证。

地图保留 FAST-LIVO2／FAST-LIO、RK／地平线、分割／单目深度／SuperPoint／MixVPR 等用户关注点，不解释为已选技术。此轮没有评估算法性能或核实具体产品硬件。

持久保留三条重要输入：用户已决定尝试加入灵光；若顺利，计划 2026-10-17 入职；“约 12 个上海办公日”是历史估计且日期基准未知。2026-09-23 不能据此推算现在还有 12 个准备日，也不自动排一份满负荷日历。

“首款产品主打 LiDAR＋单目、没有 RTK”登记为用户转述张总的信息，具体型号、同步、算力等未知。可建议先从建图定位与产品流程这个交叉问题开始，明确这是 Agent 推荐，尚非用户选定优先级。八个方向不产生八条已承诺行动。

### B. 深入一个跨领域问题

假设用户开始讨论“没有 RTK 时，首轮建图、重定位和地图复用怎样衔接”。形成 C2“首款建图定位流程与约束”，关联 C1，在工作区维护一份演进方案。

同一方案展开用户首次建图、地图保存与失效条件、定位恢复、失败时产品交互，以及传感器时间同步与软件接口需要核实的地方。算法候选留在备选讨论中，不凭名称认定适用。

可产出流程图、接口草案和实验问题列表，仍标为探索中。明确计划可以直接登记行动，不要求用户先写验收标准。例如“明天找同事聊一下同步问题”登记为 A0，Agent 自行提炼“完成这次交流”的条件；用户后来明确说“聊完了”，记录“用户报告已完成”及其来源，但同步技术问题仍按证据保持未解决或待核实。重要实验另按技术验收条件判断；“研究 SLAM”不充当一个永久不关闭的任务。

下次可以继续争论方案本身，而非从任务状态或最终结论猜测此前讨论。

### C. 补充零散材料或实测结果

假设用户补充截图、硬件表和一段录制数据。Agent 先检索已有材料，原件保存后登记 S1—S3，注明来源和缺失条件；不让用户选择数据库类别。

假设分析得到“某一录制片段发生定位失效”。保存实验方法、代码／参数版本、硬件和标定、数据片段、观测及限制，并链接结果文件 R1。缺少时间同步说明时如实写明；不能从一次失败宣布整条路线不可用。

如果 R1 反驳方案中的假设 H1，更新 C2 当前理解并指出“这份结果削弱了此前假设，原因是……，但尚未排除……”。如果输入是用户口述“这次跑通了”，只记用户报告的结果，不能声称 Agent 已实测。

### D. 阶段选择，随后更正

假设用户说“准备期先用 FAST-LIO 建一个基线，再评估视觉增益”。登记阶段决定 D1，范围只限入职前验证，理由来自本次讨论，不变成生产选型；行动 A1 是基线验证，完成标准是交付带条件和限制的结果，不是证明方案一定成功。

随后用户说“我不是决定无视觉方案，只是先把同步和标定查清”。若之前记录过度解读，就以纠正记录修订 D1；若确实改了计划，就保留 D1 并由新决定 D2 取代。无法从语境区分且会影响执行时才问。

更新方案和当前理解中对 D1 的引用，把尚未开始且依赖旧前提的 A1 调整为受阻或取消并记录原因；已完成实验结果仍保留其历史适用条件。新决定改变后续安排，不改写过去实验事实。旧成果标记“基于已替代决定／需复核”；阅读投影等待刷新。

### E. 换对话、换 Agent 后继续

用户只说“继续上次定位的事”。新 Agent 通过 C2 入口读取 D2、相关来源、当前方案和剩余问题，直接推进同步与标定的核查，不重放八项准备。

若用户说“我忘了为什么改方向”，先回答“上次选择只覆盖准备期验证；后来你澄清应先核对同步和标定，所以基线验证暂等这些条件”。细节追问再展示历史记录和依据。

若一个月后恢复，明确计划入职日已经过去，但没有入职确认记录，不能自行把“准备期”改成“已入职”；实际工作问题仍可继续，同时简短核对这一阶段变化。若 C2 有记录但实验原文件缺失，具体指出缺的是 R1 对应数据，不能假装重新复现过。

### F. 生成供其他设备阅读的结论

生成“建图定位准备简报”，首屏给出当前阶段判断、为什么先核对条件、尚不能证明什么和下一步。关联当前版本 D2、相关材料和方案，只暴露阅读所需内容。

本地核心通过后，获授权的展示增量把这份内容投影到一个 Lumos Project 下的一篇规范子页，并验证更新同一页面和手机阅读。成果链接按实际可访问渠道提供，缺少附件渠道就说明文件仅在主位置，不承诺随包附件。页面没有第二套任务维护按钮，发表简报也不意味着内部问题已结束。HTML 导出不属于这次验收，展示未启用不影响 A—E、G 的本地流程。

### G. 完整工程与数据迁移后恢复

在旧位置冻结 Agent 和人工写入，按整组清单核对生成并校验快照及工程包，覆盖当时实际存在的 C1／C2、相关决定／行动、依据、成果、草稿和历史版本；不为凑齐示例 ID 制造数据。换一个数据根恢复，不提供原会话，旧位置从冻结开始到新位置接管后始终只读。

新 Agent 应找回现行判断与决定、旧判断更正的原因、真实行动状态、结果条件及已有成果文件。隔离试运行中保存一次变化并验证，缓存删除后仍可恢复理解；Notion 不连通不影响本地工作。验证成功后保留有效试运行变化，由新位置接管，旧位置继续只读。

另演练一次取消：停止新位置，放弃其试运行工作状态，有独有内容则留非权威差异归档并说明未纳入旧位置；随后才解冻旧位置。如需采纳归档内容，重新核对后按普通保存流程吸收。缺少必要原件或工程版本不匹配时迁移失败，不以“数据库能打开”代替迁移成功。

## 10. 第一版边界与验收

### 第一批：两条真实脉络的本地闭环

围绕“入职准备”和实际展开的“建图定位”两条脉络，按真实输入依次验证：

1. 保存一次有意义的讨论、当前理解及必要依据，八方向仍是一份地图。
2. 登记一个明确的普通行动，并能按用户明确报告记录完成依据。
3. 纠正一次判断，保留原因并修订受影响的当前文档／行动；若实际尚未发生纠正，用明确标记的隔离样例演练，不伪造用户历史。
4. 新对话或另一位 Agent 不依赖旧聊天，直接继续同一问题。
5. 完整备份并换目录恢复，验证后继续保存一次变化；演练迁移接管及取消，任何时点不出现两个正式可写位置。

为此只实现简短 Agent 入口、Markdown 工作文件、最小 SQLite 记录和实际引用、按问题读取、单编辑保存与读回、必要版本／变更保留，以及成套备份恢复和兼容性检查。关系仅服务这两条脉络中的依据、行动、纠正与文件定位；不先做通用关系管理功能。

在上述闭环中同步验证防覆盖、保存中断、整组备份一致性与迁移切换，不把可靠性延期到平台扩展后。不可变文件版本＋数据库指针仅是小型保存工具的一部分，不建设通用版本管理系统。

### 本地通过后的展示增量

获授权后建立一个 Lumos Project 和一篇展示子页，验证结论、依据边界、更新时间、成果入口及一次原页更新。它有单独的展示验收，不作为本地闭环和迁移通过的前置条件。

### 后置

HTML 阅读包及附件打包／传输按需后置；手机补充信息先考虑独立收件箱、由主位置吸收；多设备并发、移动执行、常驻提醒、云端共享数据库、专用 UI、向量检索、图谱、全量聊天归档、自动规则学习和多 Agent 调度均后置。

当反复找不到对象时再增强检索；当文件浏览／审批成为明确瓶颈时再考虑 UI；当需要离线于对话的定时行为时再论证后台服务。当前不为假设中的规模预建平台。

### 实现后的必要验收，不是本轮已通过的测试

| 验收 | 必须观察到的结果 |
| --- | --- |
| 本地闭环（A—E、G 的最小真实实例），由新对话或另一位 Agent 接续 | 不用旧聊天即可接续；八方向未变成八个永续任务；不为填满示例制造实验或决定 |
| 建议、决定、来源和实测边界 | 不误提升 Agent 提案；报告结果与复现实测分开 |
| 普通行动登记与完成 | “明天聊同步”直接登记，“聊完了”记用户报告完成；不要求补验收标准，不误关闭技术问题 |
| 阶段纠正及依赖传播 | 旧理由可追溯，相关行动和当前文档被修订，长期脉络不误关闭 |
| 编辑期间人工改变基线 | Agent 读后注入人工补充，候选保持独立；替换前检出变化，基线／双方保留并重新合并；不能满足单编辑约束时不替换 |
| 保存中断 | 不可变版本写入后、事务提交后及工作副本部分刷新时中断，均能恢复完整正式批次，未提交／冲突内容不丢失 |
| 第二 Agent 使用旧基线 | 编辑会话不重叠；迟到提交被要求重读，不能覆盖已提交变化 |
| 整组备份一致性 | 复制 A 后修改 A／B，以及扫描期间增删文件，前后完整清单核对失败，整组重试或标记不完整 |
| 缺文件、损坏文件 | 明确失败，不生成“完整”假快照 |
| 新目录恢复、删除缓存、无 Notion／旧会话 | 当前理解、依据和成果仍可访问，能继续保存 |
| 迁移成功、失败及取消 | 旧位置全程只读；成功由新位置唯一接管；失败／取消先停新位置并归档独有差异，再恢复旧位置写入；冻结状态不因重启失效 |
| 版本不兼容与成套恢复 | 不兼容拒写；存在实际 schema 升级时再验证升级失败与成套回滚，不预建迁移框架 |
| 展示增量（F，单独验收） | 一个 Lumos Project 和一篇子页可在手机阅读并原页更新；成果入口真实可访问或明确不可用；无 HTML 必做项 |

技术检查通过之外，还需用户实际体验确认：恢复背景不啰嗦，纠正不费力，文档确实帮助继续探索。先完成一次真实跨会话工作和一次恢复演练，再决定扩大范围。

## 11. 主要取舍与需要用户决定的少数事项

主要取舍：本地优先减少运维，代价是主位置不运行时无主动任务；SQLite 与文件分工提供可查询状态和开放写作，代价是需要小型保存工具；单编辑和静止备份避免建设协同系统，代价是这些操作期间人工须暂停写入；保留文件版本使迁移和追溯可靠，代价是磁盘占用；选择性保存降低噪声，但不能保证还原全部原话；Notion 单向展示避免状态分叉，但手机编辑不能直接成为内部事实。

第一轮意见全部采纳，没有保留的设计分歧。基本路线无需再次投票；本轮交回 reviewer 复审编辑防覆盖、整组快照及迁移单主切换是否已覆盖失败场景，复审前不启动实现。

实际部署前仍需确定独立备份落点、是否允许含内部工作资料的异地存储；启用展示增量前需明确 Notion 展示范围与授权。这些现实输入未确定时不宣称已有设备故障保障或实际发布，也不把它们变成当前设计修订的问卷。数据根等普通实现选择届时直接给出默认推荐。

准备优先级、实际可用时间、准确硬件和入职状态是后续真实工作输入，不是设计评审前必须填完的问卷；未知就保留未知，不据此阻塞最小架构评审。
